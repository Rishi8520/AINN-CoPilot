🎬 Real-Life Scenario Walk-Through

NOC engineer asks: "Cell sector gNB-7 is showing high BLER in sector 3. Diagnose and suggest corrective action."

🧑
Engineer → Streamlit UI (localhost:8501)
Types the query and hits Enter.
Nothing has happened yet. This is just your browser talking to a local container.
⚡
UI → Gateway (Docker bridge) → Agent
Query is forwarded inside Docker. Gateway logs the request, checks rate limit, passes to Agent.
POST /v1/chat {"query": "Cell gNB-7 sector 3 high BLER, diagnose"}
🧠
Agent → vLLM on Member 2's machine (LAN)
Agent sends the query to the LLM. LLM decides: "I need simulation data AND 3GPP spec context to answer this."
→ tool_call: simulate_network(gNB="gNB-7", sector=3, scenario="bler_stress") → tool_call: rag_retrieve(query="BLER threshold remediation 5G NR TS 38.321")
Both tool calls can fire in parallel — agent doesn't wait for one before starting the other.
🔬
Agent → FastAPI/Simu5G on Member 1's machine (LAN)
Simulation runs for ~10s. OMNeT++ spins up the gNB-7 sector 3 scenario headlessly.
POST http://M1_IP:8888/simulate {"gnb": "gNB-7", "sector": 3, "scenario": "bler_stress", "duration_s": 10} ← {"bler": 0.18, "sinr_db": 4.2, "prb_util": 0.91, "handover_fail": 3}
BLER=0.18 (18%) is way above the 2% threshold. PRB utilisation at 91% — cell is overloaded.
🔡
Agent → TEI Embedding → Redis → TEI Reranker (all Docker)
Query is vectorised → Redis returns top-10 chunks from 3GPP TS 38.321 and O-RAN WG3 specs → Reranker keeps top-3.
chunks returned: [1] TS 38.321 §6.1.3 — HARQ retransmission limits and BLER targets [2] O-RAN WG3 E2SM-KPM v3 — PRB utilisation thresholds [3] TS 38.300 §15.2 — Load balancing triggers for NR
🧠
Agent → vLLM again — synthesis call (LAN)
Agent sends both tool outputs back to the LLM: "Here are the sim KPIs + spec chunks. Now give the diagnosis."
system: You are a 5G network operations expert. tool_result[simulate]: {"bler": 0.18, "sinr_db": 4.2, "prb_util": 0.91} tool_result[rag]: [TS38.321 §6.1.3], [O-RAN WG3 E2SM], [TS38.300 §15.2] → synthesise diagnosis + corrective actions
📋
LLM → Agent → Gateway → UI → Engineer's screen
Final answer streams back to the browser. The engineer sees a structured diagnosis.
DIAGNOSIS: gNB-7 Sector 3 — Cell Overload + Poor SINR ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━ • BLER 18% (threshold: 2%) — per TS 38.321 §6.1.3 • PRB utilisation 91% → insufficient free resources for HARQ retx • SINR 4.2 dB indicates inter-cell interference likely RECOMMENDED ACTIONS: 1. Trigger inter-frequency load balancing (TS 38.300 §15.2) 2. Reduce MCS index to improve link robustness in high-interference zone 3. Activate MLB xApp via O-RAN near-RT RIC to redistribute UEs
Entire round trip: ~12–15 seconds. Sim dominates (10s). LLM calls ~1–2s each.

🐳 Docker Internal Network (ainn-net)

  • All 7 containers on M3 machine share one bridge network
  • They address each other by container name: ainn-agent, redis-vector-db
  • Nothing on this network is reachable from outside — only :8501 is published
  • Defined once in docker-compose.yml under networks: ainn-net:

🌐 LAN Cross-Machine Calls

  • Only 2 calls cross the LAN: to M1 (sim) and M2 (LLM)
  • Both configured via .env: SIM_SERVICE_URL and LLM_ENDPOINT_URL
  • M1 needs Windows portproxy: WSL IP changes on reboot — fix with a startup script
  • M2's vLLM must bind to 0.0.0.0, not 127.0.0.1, to be LAN-reachable
